# PRINCÍPIOS FUNDAMENTAIS

## 1. Simplicidade Acima de Complexidade

Toda decisão arquitetural deve responder:

> Existe uma forma mais simples de resolver isso sem perder qualidade?

Abstrações desnecessárias devem ser evitadas.

Patterns só devem existir quando resolvem um problema real.

---

## 2. Escalabilidade Evolutiva

O sistema deve ser preparado para crescer sem exigir reescrita completa.

As soluções devem:

* Permitir novas funcionalidades
* Facilitar manutenção
* Reduzir acoplamento
* Favorecer testes automatizados

---

## 3. Clareza Acima de Inteligência

Código deve ser compreendido rapidamente por qualquer desenvolvedor.

Se uma implementação exige explicações constantes, provavelmente está complexa demais.

---

## 4. Regra de Negócio é Patrimônio da Empresa

As regras de negócio são o ativo mais importante do sistema.

Devem estar:

* Centralizadas
* Documentadas
* Testadas
* Isoladas da interface

---

# ARQUITETURA OFICIAL

## MVC Real

O projeto deve respeitar rigorosamente a separação de responsabilidades.

### Model

Responsável por:

* Entidade
* Relacionamentos
* Scopes
* Accessors
* Mutators

Não deve concentrar regras de negócio complexas.

---

### Controller

Responsável por:

* Receber requisições
* Acionar Services
* Retornar Responses
* Redirecionamentos

Não deve conter:

* Regras de negócio
* Consultas complexas
* Processamentos extensos

Controller deve permanecer enxuto.

---

### Service Layer

Toda regra de negócio relevante deve estar em Services.

Exemplos:

```text
TicketAssignmentService
UserRegistrationService
NotificationService
```

Services são responsáveis por:

* Regras de negócio
* Processos transacionais
* Orquestração de operações

Devem ser facilmente testáveis.

---

### Form Requests

Validações devem ser centralizadas.

Exemplos:

```text
StoreTicketRequest
UpdateTicketRequest
StoreUserRequest
```

É proibido validar diretamente nos Controllers.

---

# REGRAS ARQUITETURAIS INEGOCIÁVEIS

## Controller God é Proibido

Se um Controller:

* possui muitas responsabilidades
* possui muitas consultas
* possui muitas regras

ele deve ser refatorado.

---

## Regras de Negócio Não Podem Vazar

É proibido colocar regras de negócio em:

* Blade
* JavaScript
* Controllers
* Migrations
* Seeders

Toda regra deve possuir local único.

---

## Fonte Única de Verdade

A regra de negócio deve existir apenas no backend.

Frontend apenas apresenta informações.

Nunca confiar exclusivamente em validações da interface.

---

# BANCO DE DADOS

## Modelagem

A modelagem deve priorizar:

* Integridade
* Clareza
* Escalabilidade

---

## Relacionamentos

Sempre utilizar relacionamentos Eloquent quando apropriado.

Evitar consultas repetidas.

---

## Índices

Sempre avaliar:

* Campos de busca
* Chaves estrangeiras
* Ordenações frequentes

Toda consulta recorrente deve considerar impacto de índice.

---

# PERFORMANCE

## Consultas

Evitar:

* N+1 Queries
* Eager Loading ausente
* Consultas duplicadas
* Processamento em loops desnecessários

Sempre avaliar:

```php
with()
withCount()
select()
exists()
```

antes de soluções mais custosas.

---

## Escalabilidade

Antes de implementar uma funcionalidade, avaliar:

* Quantidade de registros
* Crescimento futuro
* Consumo de memória
* Quantidade de consultas

---

## Otimização

Otimizar apenas quando necessário.

Mas nunca ignorar problemas evidentes.

---

# TRANSAÇÕES

Quando uma operação altera múltiplas entidades relacionadas:

Utilizar:

```php
DB::transaction()
```

Objetivo:

* Atomicidade
* Consistência
* Recuperação em caso de falha

Toda transação deve possuir comentário explicando sua necessidade.

---

# TESTABILIDADE

Toda regra crítica deve ser testável isoladamente.

Priorizar:

## Testes Unitários

Para:

* Services
* Regras de negócio
* Cálculos
* Distribuições automáticas

---

## Testes Feature

Para:

* Fluxos HTTP
* CRUDs
* Autenticação
* Autorização

---
